# Blockwright Windows installer

`Blockwright.iss` defines a Windows x64 Inno Setup package with a stable `AppId`. Interactive setup offers **all users** (the elevated default under `{autopf}`) or **current user** (no elevation, under the current user's Programs directory). Silent automation can select the same modes with `/ALLUSERS` or `/CURRENTUSER`. The installer consumes only the staging directory created by `scripts/release/build-windows-release.mjs`; do not point it at an arbitrary source checkout.

The installer owns its application directory and the allowlisted state entries recorded by `Initialize-Blockwright.ps1`. Ordinary uninstall preserves projects, exports, and palettes. `/REMOVEUSERDATA` is the explicit opt-in to delete that user content plus the exact legacy `%APPDATA%\Blockwright\palettes.json` file.

An all-users install changes only machine-wide application files, shared shortcuts, and explicitly selected machine-wide sign-in entries. Configuration, credentials, and projects stay per user; each session loads packaged defaults and creates account-owned state as needed. Codex registration and `.schem` association can be enabled later by each user with the packaged helpers. The elevated installer deliberately does not write an administrator account's user-area state on somebody else's behalf. Accordingly, all-users uninstall removes the shared application and sign-in entries but preserves every account's per-user data and integrations.

The Start Menu shortcut, optional desktop shortcut, optional sign-in entries, updater relaunch, and `.schem` association all target the packaged `Blockwright.exe`. That product-owned x64 WinExe contains the real Blockwright icon/version metadata and delegates to one existing PowerShell/WPF Control Center per installation; it is not a replacement native UI or service. Closing the WPF window hides it to the notification area; choosing **Exit** there stops only the ownership-verified Node.js server process tree started by that controller. Two independent, unchecked setup tasks can launch the visible Control Center at sign-in or start the engine minimized in the notification area; selecting neither leaves sign-in unchanged. This remains a logged-in-user supervisor, not a Windows service and does not survive sign-out. Sanitized rotating logs and crash metadata live under each user's state root and remain eligible for the existing diagnostics/support-bundle and uninstall cleanup paths.

Local builds are unsigned, untrusted, and remain labeled that way for both the nested launcher and the outer installer. The historical public v0.6.0 MVP policy is a one-version unsigned prerelease exception; it does not extend to v0.8.0 or later. That exception's GitHub page and setup instructions must conspicuously say that Windows reports an unknown publisher and may show SmartScreen, publish the exact tested `SHA256SUMS.txt`, both SBOMs, and `blockwright-0.6.0-signature-status.json`, and direct users to continue only after verifying the hash and deciding to trust this repository. It is not eligible for the built-in updater or WinGet.

Signed stable releases remain the preferred channel. The manually dispatched signed-release workflow imports a real protected publisher certificate only inside the `windows-signing` environment, confirms its thumbprint, signs and timestamp-verifies the native launcher before packaging, proves those exact signed launcher bytes are inside the portable archive, signs and timestamp-verifies the final installer, regenerates checksums/update metadata from signed bytes, reruns lifecycle validation, and creates a draft for the separately approved publication workflow. Creating a tag alone never starts that credentialed pipeline.

Release prerequisites and human gates are documented in [SIGNING.md](SIGNING.md), [WINGET.md](WINGET.md), and [assets/README.md](assets/README.md).
